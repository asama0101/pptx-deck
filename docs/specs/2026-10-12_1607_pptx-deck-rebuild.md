# pptx-deck 作り直し SPEC

## 概要
- 目的: ビジネス上の承認文書（稟議・提案・計画）向けに、コンサルテイストのスライドを、原稿の承認 → HTML スライド案の選択 → 最終 HTML → PPTX の順で作るスキルを、0 ベースで作り直す。
- ゴール（完了の判定）: 下の受入条件 1〜8 を満たす。
- 旧 `skills/pptx-deck` は参考にとどめ、コードやファイルはコピーしない。新スキルが旧スキルを置き換える（同じ場所・同名）。

## 流れ
1. **入力**: テーマのみ／素材（メモ・文書・データ）／既存 Markdown 原稿のいずれか。足りない前提は質問する。あわせて次を聞く。
   - 配色の指定（プリセット名、または基調色 #RRGGBB）
   - 利用者の PowerPoint テンプレートの有無（`.potx` または `.pptx` のパス。指定がなければ、スキル内蔵の標準テンプレートを使う）
2. **原稿**: `script.md` を作り、チャットで承認を得る（承認①）。承認後、内容は凍結する。
3. **スライド案**: 全スライドについて、各 3 案以上を 1 つの `variants.html` にまとめる。ユーザーは HTML 上で案を選び、「どうしてほしいか」をコメントして送信する（承認②）。
   - 3 案は、同じ型のまま配置・強調・密度を変える。基本として、図と表を多用して説明する。
   - 反映後は、コメントのあったスライドだけ、選ばれた案を直して 1 案で再提示する。別案の希望があるときだけ 3 案を出し直す。
4. **最終 HTML**: 選ばれた案を統合した `final.html` を作り、ブラウザで全スライドを確認してもらい、承認を得る（承認③）。
5. **PPTX**: `final.html` をブラウザで計測し、テンプレートのファイルを土台にして、PowerPoint の図形・文字・表・グラフとして `<名前>.pptx` に書き出す。体裁を検査し、確認用の画像を作って崩れを確認する。PowerPoint での最終確認を勧める。

## 仕様

### 変換方式（決定）
- HTML は決められた部品（文字・四角・線・図・表・グラフ）だけで書く。ブラウザで各部品の位置と大きさを測り、PowerPoint のネイティブ要素として同じ位置に置く。画像化はしない。
- 実装は **Python 一本**（python-pptx ＋ Playwright for Python）。（最終確認 1 の「Node.js」から変更。Node.js の pptx-automizer も候補だったが、レイアウトだけのテンプレートから確実にスライドを足せる python-pptx を選んだ）
- 位置の計測は、スクリプトが自分の Playwright（Python 版）でブラウザを起動して行う。`build` 1 コマンドで、計測から PPTX の書き出しまで通る（再現性と自動テストのため）。Playwright MCP は、スキルのスクリプトからは呼ばない。MCP は、Claude が `variants.html`・`final.html` を開いて、利用者の選択の送信を受け取るためだけに使う。

### 実行環境（仮想環境）
- 仮想環境は、ユーザー共通の場所 `%LOCALAPPDATA%\pptx-deck\venv` に作る。スキルを更新しても残り、プロジェクトをまたいで再利用する。スキルのフォルダやプロジェクトは汚さない。
- python-pptx・Playwright・chromium が不足していると検出したら、利用者に「環境を作ってよいか」を確認する。承認が出るまで作らない。承認後、`python -m venv` で作り、`requirements.txt` の内容と chromium を導入する。
- スキルのスクリプトは、常にこの仮想環境の Python で実行する。システムの Python に導入しない。

### 利用者のテンプレートへの従い方（決定）
- 受け取る形式: `.potx` と `.pptx` の両方。`.pptx` は、スライドマスターとレイアウトだけを使い、中身のスライドは使わない。
- 方式: テンプレートのファイルを土台に開き、そのレイアウトの上にスライドを作る。マスターとレイアウトは本物のまま残る（PowerPoint でレイアウトの切り替えやロゴの差し替えができる）。標準テンプレートも同じ仕組みで、スキル内に `.potx` として持つ。
- 従う範囲: **表紙・裏表紙（最終スライド）・ヘッダー・フッター（ページ番号を含む）まで**。本文のスライドの中身は、スキルのテンプレート（レイアウト・図解・表・グラフ）で作る。
- フォント・配色: テンプレートの指定にかかわらず、BIZ UDPゴシックと、選んだ配色（プリセット／基調色）を使う。
- HTML のプレビュー: テンプレートの表紙・裏表紙・ヘッダー・フッターを画像化（LibreOffice）して下地に敷き、本文を置ける範囲をテンプレートから読み取る。
- 該当するレイアウトがテンプレートにないときは、本文のレイアウトに代え、その旨を報告する。

### スキルのテンプレート（スキル内の Markdown と同じ場所に置き、参照する）
- レイアウト: 表紙・目次・章扉・本文・結論／承認依頼・付録。表紙と裏表紙は、利用者のテンプレートがあればそれに従う。
- 図解: 実際に使う 10 種前後（フロー・ツリー・マトリクス・ピラミッド・サイクル・ガント・ベン図・ビフォーアフターなど）から始める。
- 表: 比較表・評価表（◎○△）・費用表・スケジュール表。
- グラフ: 棒・折れ線・円・積み上げ・ウォーターフォール。PowerPoint のグラフとして出す（編集できる）。
- アイコン: 自作の線画 SVG を同梱する。
- 配色: HTML の変数で一元管理する。プリセット数種（例: 紺・緑・グレー）から選ぶか、基調色を 1 つ指定すると、薄色・濃色・強調色を自動で作る。文字のコントラスト比 4.5:1 は確認する。

### コンサルテイスト（守ること）
- 見出しは結論を言い切る 1 文（アクションタイトル）。1 スライド 1 メッセージ、結論 → 根拠の順。
- 数字には出典と前提を添える。
- 配色は無彩色＋基調 1 色＋強調 1 色まで。グラデーション・影・3D は使わない。
- 判断が要るスライドには、決めること・期限・推奨を置く。
- 密度は高めで、余白と整列をそろえる。文字は本文 14pt 以上。

### 原稿（`script.md`）の項目
- スライドごとに、見出し、章名（そのスライドが答える問い）、本文、図・表・グラフの指定（型と選んだ理由を 1 行）、出典・前提、判断の枠（判断が要るスライドのみ）。
- スピーカーノートは作らない。

### 体裁の検査（最小限）
- 文字のはみ出し、図形の重なり（本文と、テンプレートのヘッダー・フッターの重なりを含む）、文字サイズの下限、文字のコントラスト。コンサルテイストの検査（出典の有無など）は、今回は作らない。

### 共通の前提
- Windows 専用、フォントは BIZ UDPゴシック、16:9（13.33×7.5in）、本文を画像にしない。

### ファイルの置き場所
| 置き場所 | ファイル |
|---|---|
| スキルの Markdown と同じ場所（`skills/pptx-deck/`） | `SKILL.md`、テンプレート（レイアウト・図解・表・グラフ・アイコン・配色・標準 `.potx`）、変換と検査のコード、`requirements.txt` |
| ユーザー共通の場所（`%LOCALAPPDATA%\pptx-deck\venv`） | 仮想環境（python-pptx・Playwright・chromium） |
| OS の一時フォルダ（`%TEMP%\pptx-deck\<名前>\`） | 確認用の PNG、テンプレートの下地画像、検査結果などの一過性のもの |
| 実行したディレクトリ直下の `<名前>/` | `script.md`、`variants.html`、`final.html`、`<名前>.pptx` |

- 同名のフォルダがあるときは、上書きの前に中身を確認する。

## 受入条件
1. 新 `skills/pptx-deck/SKILL.md` が、上の流れ（承認①〜③）と置き場所を、旧仕様の記述なしで定めている。
2. スキルのテンプレート一式（レイアウト・図解・表・グラフ・アイコン・配色プリセット・標準 `.potx`）が、スキル内にあり、HTML から参照できる。基調色の指定で、配色が全テンプレートに反映される。
3. サンプル原稿 1 本（10 枚前後）で、原稿 → 3 案の `variants.html`（HTML 上で選択とコメントを送信できる）→ `final.html` → PPTX が最後まで通る。
4. 出力 PPTX は、PowerPoint の図形・文字・表・グラフで構成され（本文が画像でない）、検査（はみ出し・重なり・文字サイズ・コントラスト）に違反がない。LibreOffice の画像で崩れていない。
5. 利用者のテンプレート（`.potx` と `.pptx` の各 1 本で確認）を指定すると、PPTX の表紙・裏表紙・ヘッダー・フッターがそのテンプレートのマスター／レイアウトに従う。本文のフォントと配色は、BIZ UDPゴシックと選んだ配色になる。
6. 旧スキルのファイル（旧 SKILL.md・旧テンプレ・旧コード・旧テスト）が、新スキルから参照されず、置き換えられている。
7. 仮想環境がない状態で実行すると、作ってよいかの確認が出て、承認後に `%LOCALAPPDATA%\pptx-deck\venv` へ導入される。導入後は、`build` 1 コマンドで計測から PPTX の書き出しまで通る。
8. `README.md` が新仕様に合っている。新コードのテストが通る。

## 非目標
- 旧スキルのコードやファイルのコピー、旧仕様（構成案の承認、判断の枠のルール、橙の役割ルールなど）の引き継ぎ。
- スピーカーノート、コンサルテイスト自体の自動検査、写真素材の自動収集、外部サービスへの送信。
- 既存 PPTX の編集。利用者のテンプレートの本文スライドの中身の流用、テンプレートのフォント・配色の適用（従うのは表紙・裏表紙・ヘッダー・フッターまで）。
- 配色の全色自由指定（基調色の指定まで）。

## リスク
- 3 案 × 全スライドの生成と承認が重い → 全スライドを 1 つの HTML にまとめ、選ぶ往復を 1 回にする。直しは 1 案だけ再提示する。
- HTML と PPTX の見た目のずれ → 部品を限定し、ブラウザで測って写す。変換できない書き方は作らない。
- 配色変更時の反映漏れ → 色は変数だけで持ち、直書きしない。
- 利用者のテンプレートの構造が想定外（レイアウト名が違う、ヘッダー／フッターがプレースホルダーでない、本文領域が読み取れない）→ 該当レイアウトが見つからないときは本文のレイアウトに代えて報告する。サンプル 2 本（`.potx`・`.pptx`）で確認する。
- テンプレートの本文領域と、本文の部品が衝突する → 重なりの検査にヘッダー・フッターの領域を含める。
- 旧スキルの資産を捨てすぎる、または流用しすぎる → 参考にとどめ、コードはコピーしない（利用者の指示）。
- 変換の仕組みを作る手間が大きい（方式 A の代償）。
- 初回の環境導入（chromium は数百 MB）が重い → 共通の場所に 1 回だけ作り、再利用する。承認なしに作らない。
- スキルは Playwright MCP がある環境が前提（案の選択の受け取りに使う）。MCP がない環境では、`variants.html` の選択を受け取れない。
