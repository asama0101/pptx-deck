# PPTX作成スキル SPEC（改訂版）

この SPEC は `2026-10-11_2147_pptx-skill.md`（初版）を、敵対レビューの指摘を踏まえて改訂したもの。初版と食い違う箇所は、この改訂版を正とする。

## 概要
- 目的: テーマまたは原稿から、AI っぽくない・編集可能な .pptx を高品質に作る Claude Code スキルを作る。
- ゴール（完了判定）: 受入条件（下記）をすべて満たす。
- 対象 OS: Windows のみ（Mac は対象外）。
- 配布形態: 他人にも配布できる形。`C:\Users\sioay\OneDrive\github\pptx-create` を git リポジトリにし、プラグイン構成（`.claude-plugin` + `skills/`）で作る。外部公開は完成後に別途判断し、承認を取る。OneDrive 配下の git は同期競合で `.git` が壊れる恐れがあるため、README に注意を書く。
- 公式 `anthropic-skills:pptx` には依存せず、独立したスキルにする。description は「資料作成・デザイン品質」に絞る。公式スキルと発火が重複しないかは、実装後に検証する。

## 流れ
1. 入力: テーマのみ／Markdown・テキスト原稿のどちらでも受ける。
2. 構成案（スライド一覧とメッセージ）を作り、承認を得る。入力がテーマのみの場合だけ行う。
3. 原稿を作り、内容レビュー（論理の流れ・抜け漏れ・読み手視点、1 役、1〜2 ラウンド）を行う。そのうえで原稿を承認してもらい、内容を凍結する【承認①】。
4. HTML プレビューを作る。HTML は決められたクラスだけを使う制限付きとする。DOM 計測による幾何検査に合格してから、承認に出す【承認②】。プレビューのチャートは近似であることを明示する。
5. PPTX を出力する。Playwright（Edge を使用）で HTML を描画し、各要素の位置・サイズ・フォント・色を DOM から計測して、pptxgenjs でネイティブの図形・テキスト・チャートに写す。
6. 出力後の検査を行う。(a) 生成した PPTX を XML として読み直す検査、(b) 公式 pptx スキル相当の validate、(c) LibreOffice による PPTX→PDF→PNG の画像化。違反があれば HTML を修正して再出力する。再出力は最大 3 回までとし、超えたら停止して違反を提示する。
7. 結果を報告する（承認は求めない）。検査結果、画像化は LibreOffice による近似であること、PowerPoint で開いて確認することを勧める旨を含める。

承認は 2 回（テーマのみの依頼は構成案を加えた 3 回）。修正は HTML 段階で完結させる。PPTX の再出力は、出力後検査で違反が出たときに限る。

## 仕様の決定事項
- 入力: テーマのみ／原稿。
- スライドサイズ: 13.33×7.5in（16:9）に固定。
- デザイン: 既定デザインシステムを 1 つ内蔵する。配色は無彩色＋アクセント 1 色（アクセント色は指示で変更可）。フォントは BIZ UDPゴシック。サイズは、タイトル 24〜28pt、リード 18〜20pt、図解部 14〜16pt、本文 14pt 以上、注記・キャプション 10pt 以上。
- フォント運用: BIZ UDPゴシックはこの PC にインストール済み（確認済み）。実行時にフォントの有無を確認し、なければ代替（游ゴシック／メイリオ）に切り替えて再計測する。フォントは同梱しない。PPTX に書くフォント名の表記（日本語名か英語名か）は、スパイクで確認する。
- テキストの折り返し: PowerPoint に任せる。テキストボックスは幅を指定し、HTML での計測幅に余裕率を持たせる（初期値 92% 以内。スパイクで確定）。見出しだけは、改行位置を明示した場合に行を固定する。内部余白は 0 とし、行間の写像規則は実装時に SPEC へ追記する。
- 図解: 型は 4 種（フロー、2×2 マトリクス、ピラミッド、ツリー）。HTML では「矩形・角丸矩形・円・直線矢印・テキスト」の組合せだけを使う。型は HTML 部品として用意し、内容から型を選ぶルールを SKILL に持たせる。
- グラフ: PowerPoint のネイティブチャート（編集可能）。型は 3 種（棒の縦／横、折れ線、円）。注目データだけ有彩色、他は無彩色とし、データ→色の規則を SKILL に書く。積み上げ棒・第 2 軸は、PowerPoint で破損しやすいため初版では除外する。
- 画像・アイコン: ユーザーが渡した画像の配置と、アイコン（SVG→画像）に対応する。写真素材の自動入手はしない。アイコンは画像だが本文ではないため、「画像化された本文がない」には抵触しない。
- スピーカーノート: 原稿の補足から自動生成する（pptxgenjs の addNotes）。
- アクセシビリティ: 画像の代替テキストを付ける。アクセント色を変えたとき、コントラスト比 4.5:1 以上を検査する。
- エラー処理: ブラウザ起動失敗、フォント未導入、入力が空または巨大な場合は、原因と対処を示して停止する。
- 中間成果物: 利用者の作業フォルダ内の `deck-work/<名前>/` に、構成案・原稿・HTML・検査結果を置く（再開できる）。内部の一時ファイルだけ OS の一時フォルダに置く。
- 実行環境: Node（この PC は v24.13.1）、Playwright（Edge を使用、バージョン固定）、pptxgenjs（4.0.1 を固定）、LibreOffice（推奨依存。この PC は 26.8.1.1 を導入済み）。依存はバージョンを固定し、導入スクリプトを用意する。

## 体裁チェックの合格基準
検査対象は、生成後の PPTX を XML として読み直した値。しきい値は設定ファイルに出し、後から調整できるようにする。
- はみ出し: 図形がスライド外、または安全マージン（四辺 0.4in）外にある。親の枠より 1pt を超えてはみ出す子要素。
- 重なり: 兄弟の図形の矩形が、面積比 5% を超えて交差する。背景カード・装飾（`data-decor` 指定）・矢印・コネクタ・グループ内は除外。
- 最小フォント: 本文 14pt 未満、注記・キャプション 10pt 未満、チャートの軸ラベル 10pt 未満。
- 階層: タイトルと本文のサイズ差が 4pt 未満。
- 画像本文: 画像（`<p:pic>`）が本文テキストの代わりに使われていないこと。
- 破損: validate が通ること。

## 「AIっぽくない」の客観チェック
- 階層: タイトル位置がスライド間で揃う。タイトルと本文のサイズ差が 4pt 以上。
- 単調: 同じレイアウトを 3 枚以上連続で使わない。10 枚以上では図解かグラフが 2 枚以上ある。
- 余白: 各スライドの内容領域の使用率が 40〜85%。
- 色数: 無彩色＋アクセント 1 色（有彩色が 2 色以上なら違反）。
- 避けること（公式 pptx スキルに準拠）: タイトル下のアクセント線、装飾バー、本文のセンタリング、タイトル末尾のピリオド。
- 主観判定: サンプル 3 本それぞれで、10 枚中 8 枚以上が修正不要。ユーザー自身が判定する。

## オーバーフロー時の自動修正
優先順位は、余白 → 行間 → フォント縮小（下限まで）→ それでも収まらなければ分割案・削減案を提示してユーザーに承認を求める。原稿の内容は、承認なしでは変えない。自動修正は最大 3 回まで（出力後検査の再出力と合わせた上限）。

## 受入条件
- サンプル依頼 3 種（テーマのみ／長めの原稿／図解・グラフ多め）を固定ファイルとしてリポジトリに置く。それぞれに期待枚数の範囲（目安 10〜15 枚）を付け、PPTX が生成できる。
- 体裁チェックの合格基準で、違反が 0 件（例外は `data-decor` などの明示した除外のみ）。
- 生成した PPTX が validate を通り、本文が画像になっていない。
- 「AIっぽくない」の客観チェックをすべて満たし、主観判定（10 枚中 8 枚以上が修正不要）を満たす。
- 着手前のスパイクで、日本語段落の折り返しが、HTML の計測と LibreOffice の描画で許容範囲に収まることが確認できている。

## 開発時の確認（スキルの実行フローには含めない）
- 日本語段落 10 種を、HTML の計測と LibreOffice の描画で比べるスパイクを、実装の最初に行う。余裕率（初期値 92%）をここで確定する。
- Web 版 PowerPoint（OneDrive にアップロードして開く）で、人が最終の見た目を確認する。これはスキル作成時の確認であり、完成したスキルの実行フローにはこの手順を入れない。

## 非目標（初版）
- テンプレ（.pptx/.potx）への対応。第 2 版で、zip 展開して XML を直接編集するルートとして別途設計する。pptxgenjs は既存ファイルのマスタを継承できないため、初版の方式では実現できない。
- 既存 PPTX の修正・再デザイン。
- Word/PDF/Excel など他形式からの変換。
- 多役レビュー（ファクトチェック・敵対的レビュー、最大 5 ラウンド）。初版の内容レビューは 1 役。
- 複数デザインプリセット、毎回のデザインシステム生成ヒアリング。
- 写真素材の自動入手。
- 積み上げ棒・第 2 軸のチャート、サイクル・ベン図などの図解。
- Mac 対応。
- 外部への公開（完成後に別途判断）。

## リスク
- 折り返しの不一致: HTML と PowerPoint で行の分かれ方が違う。余裕率とスパイクで対処する。LibreOffice も PowerPoint の近似にすぎず、最終確認は人が行う。
- 画像化は近似: LibreOffice の描画は PowerPoint と完全には一致しない。報告で明示する。
- AI っぽい見た目: 既定デザインの数値ルール、図解カタログ、客観チェックで対処する。
- 編集しづらい PPTX: 画像化せず、ネイティブ図形・チャートに統一する。
- DOM 計測型は使える HTML/CSS に制約が出る。デザインシステムに沿った HTML のみ書くルールで吸収する。
- Playwright の導入: ブラウザのダウンロードを避けるため Edge を使う。ただし、この方式が動くかは未検証（スパイクで確認する）。
- フォント: 受け手の環境に BIZ UDPゴシックがないと別フォントに置換され、折り返しが変わる。フォントは同梱しない（ライセンス）。
- PowerPoint の COM はこの PC に登録されていない。使わない。
- トークン消費: 承認点を最小にし、再出力と自動修正の回数に上限を設ける。
- OneDrive 配下の git: 同期競合で `.git` が壊れる恐れがある。
