# pptx-deck

ビジネス上の承認文書を、コンサル資料のテイストで作る。本文を画像にせず、PowerPoint で編集できる .pptx を出す。13.33×7.5in（16:9）、BIZ UDPゴシック、無彩色＋基調 1 色＋強調 1 色。

以降の `<skill>` は、この SKILL.md があるフォルダ。コマンドはすべて `python "<skill>/run.py" …`。`<名前>` は作業フォルダ名（実行したディレクトリ直下に作る）。

## 0. 初回だけ（環境）

1. `python "<skill>/run.py" doctor` を実行する。`venv` がない（終了コード 3）または `status` に不足があるときは、**利用者に「`%LOCALAPPDATA%\pptx-deck\venv` に Python の仮想環境と chromium（数百 MB）を導入してよいか」を確認する**。承認が出るまで作らない。
2. 承認後、`python "<skill>/run.py" setup --yes`。
3. `doctor` の `warnings` を利用者に伝える（BIZ UDPゴシック未導入、LibreOffice なしなど）。

## 1. 流れ（承認は 3 回）

| 段階 | やること | 承認 |
|---|---|---|
| 入力 | 下の「1.1 入力で聞くこと」 | |
| 設計図 | 図を作る前に `<名前>/design.md` を書く（ガバニングメッセージ・論点・台帳・ページごとの設計。2.1） | ①に含める |
| 原稿 | `<名前>/script.md` を書く。`lint-script` が空になるまで直す | ① 設計図と原稿を一緒にチャットで承認（内容を凍結） |
| スライド案 | 全スライドの 3 案を `slides/NN-A.html`〜に書き、`variants` で 1 つの HTML にする | ② HTML 上で選択＋コメント |
| 最終 HTML | 選ばれた案を `finalize` で統合し、`final-review.html` で全体を見せる | ③ HTML 上で承認／要修正（チャットでの承認でもよい） |
| PPTX | `build` で書き出し、検査と確認用の画像で崩れを確認する | |

### 1.1 入力で聞くこと
- 入口: テーマのみ／素材（メモ・文書・データ）／既存の Markdown 原稿。足りない前提（対象者・目的・枚数・期限・欠けている数字）は、作業を始める前にまとめて質問する。外れたときの手戻りが大きいものは推測しない。
- 配色: プリセット（`navy`・`green`・`gray`）か、基調色 `#RRGGBB`。指定がなければ `navy`。
- 利用者の PowerPoint テンプレートの有無（`.potx` または `.pptx` のパス）。あれば、**表紙・裏表紙・ヘッダー・フッター**がそれに従う。フォントと配色は、テンプレートにかかわらず BIZ UDPゴシックと選んだ配色。16:9（13.33×7.5in）以外のテンプレートは使えない。
- フッターの文言（社外秘など）があれば `build --footer`。

### 1.2 作業フォルダ
`python "<skill>/run.py" init "<名前>" --color <プリセット|#RRGGBB> [--template "<パス>"]`。同名のフォルダが空でないときは止まる。**中身を利用者に見せて、上書きしてよいと言われたときだけ `--force`**。`init` の出力の `notes`（テンプレートの代替レイアウト、`slides/` に前の作業のファイルが残っている旨）は利用者に伝える。`--force` は既存のファイルを消さない（`theme.css` などを上書きするだけ。`design.md` は、既にあれば上書きしない）ので、古い案が混ざらないよう、不要な `slides/` のファイルは利用者に確認してから削除する。

| 置き場所 | ファイル |
|---|---|
| スキル `<skill>/`（読み取り専用） | `SKILL.md`、`assets/`（`components/` の断片、`web/`、`icons/`、`template/`）、コード |
| 作業フォルダ `<名前>/` | `design.md`（設計図。`init` が雛形を置く）、`script.md`、`slides/NN-X.html`、`variants.html`、`final.html`、`<名前>.pptx`、`theme.css`・`base.css`・`icons/`・`_template/`（`init` が作る） |
| OS の一時フォルダ `%TEMP%\pptx-deck\<名前>\` | 確認用の PNG（`render/`）、SVG の画像化 |

## 2. 設計図と原稿（design.md・script.md）

図から作り始めない。先に設計図で各ページのヘッド（`見出し`）と論理を決め、それを原稿に写す。

- 数字を作らない。素材に無い数字は、前提を明記した試算にするか「xx」で残す（それらしく埋めない）。素材に無い固有名詞・出来事を足さない。

### 2.1 設計図（design.md）
書式は `assets/sample/design.md`（`init` が `<名前>/design.md` に置く雛形。中身は見本）に従う。1 枚物なら、資料全体と台帳は省く。

- 資料全体: **ガバニングメッセージ**（資料全体の結論）を 1 つ立て、各ページのヘッドをその下にぶら下げる。**論点**（決めさせること）は 3〜6 個に番号を付ける。冒頭のサマリで番号つきで予告し、最終ページで同じ番号で回収する。最終ページは、決定事項・日程・判断基準を載せた一番重いページにする。
- 台帳を先に作る: `| No | ヘッド | 文型 | 上位への集約 | 直前からの接続語 | 本体の型 | 論点 |`。縦の検証: ヘッドを縦に通読し、隣り合うページが「だから／なぜなら」で繋がる。横の検証: 同じ階層の並びは切り口 1 つ・粒度をそろえる（「何で割ったか」を 1 語で言える）。
- ページごと: ヘッド／文型／型（3 の型の一覧から）／図表タイトル（名詞句。時点と単位を含める）／レイアウト記述（縦軸・横軸・各エリアの中身・強調の 1 点）／証拠対応表（ヘッドの各節を、本体のどの要素が証明するか）／注記と出所（出所は必要なときだけ）。

### 2.2 ヘッドの規則（`見出し`）
- 主語と述語のある完全な文。1 ページ 1 メッセージ。「〜の分析」「〜について」は題名で、主張ではない。
- 事実＋判断を 1 文に持つ。判断語は、`lint-script` が見る固定リスト（例: 〜すべきだ／〜に限られる／〜に値する／〜を左右しない／〜ではなく〜だ／〜にすぎず／〜が見込める／〜できる／〜が必要だ）。正しい見出しが誤って落ちたときは、`pptx_deck/script_lint.py` の `_JUDGE` に語を足してよい。
- 30〜60 字。**まず 1 行に収める（28px で約 41 字）**。入らないときだけ 2 行（56 字幅まで。改行は文節で）。短いスローガンにも圧縮しない。ヘッドが 2 行になるときは、題の要素の高さを `height:80px` にする（断片の既定は 1 行の 44px）。
- 禁止: 「A。B」の二段構え（2 つの内容は「〜のため」「〜だが」「〜ことで」などの接続語で 1 文に畳む）／要素の数え上げ（「課題は3つ」「9工程のうち」）／体言止め／ダッシュ（—）／「本ページ」「この1枚」の自己言及。数字は主張の根拠になる実質数値だけ、1 文に 2 つまで。
- 文型を散らす（隣り合う 3 枚で同じ文型を続けない）: 因果「〜のため、〜する」／条件「〜すれば、〜が固まる」／逆接「〜だが、問題は〜にある」／起因「〜を左右するのは〜ではなく〜だ」／評価「〜は〜の範囲にあり、〜を左右しない」／提言「〜に、〜を集中させるべきだ」。
- 書き方: ①このページが答える問い（＝`章名`）→ ②答え（判断）を一言で → ③支える事実を 1 つ → ④②と③を接続語で 1 文に → ⑤1 行に収めるときは、根拠の節から削って図表タイトルへ移す（判断語と接続語は削らない）。
- 逆テスト: 本体だけを見た人が同じ文を書けるなら、判断が足りない。
- So What 帯（図の下に示唆を書く帯）は置かない。示唆はヘッドに書く。決定を求めるページだけ、下部に論点ボックス（パネル地の帯）を置き、「〜の可否」を 1 行で書く（`decision`・`rating` の断片にある）。

### 2.3 原稿（script.md）
書式は `assets/sample/script.md`（書式の手本であり、構成の手本ではない。決定のページが 2 枚目（S03）で、§2.1 の「最終ページで回収」の構成とは逆。11 枚。表紙と、見本の 10 枚の内容。架空の会社の中期経営計画）に従う。冒頭に目的・対象・`論点`（設計図の論点を番号つきの項目で）・配色を書き、スライドごとに次を書く。

- `layout`（`cover|section|agenda|content|diagram|table|chart|closing`）、`見出し`（**2.2 の規則に従うヘッド**）、`章名`（そのスライドが答える問い）、`本文`、`図表`（型と選んだ理由を 1 行）、必要なときだけ `出典`、判断が要るスライドは `判断の枠`（決めること・期限・推奨）。
- 1 スライド 1 メッセージ。結論 → 根拠の順。出典は必要なときだけ書く（既定では書かない）。スピーカーノートは作らない。
- 書いたら `python "<skill>/run.py" lint-script "<名前>/script.md"`。問題は全件出る。空になり、5.1 のヘッド・論理の確認を済ませてから、設計図と原稿を一緒にチャットで示して承認を求める。承認後は、承認なしに内容を変えない。

| `lint-script` が検査するもの | 人が見るもの（検査しない） |
|---|---|
| 書式（連番・`layout`・章名・図表の有無・配色）。本体のあるスライド（`content`・`diagram`・`table`・`chart`）の見出しの字数（30〜60）・判断語か接続語の有無・二段構え・ダッシュ・自己言及・隣り合う 3 枚の文型の連続。`論点` の個数（3〜6） | 完全文か・体言止め・数え上げ・実質数値 2 つまで・1 行（約 41 字）か 2 行（56 字幅まで）に入るか。逆テスト。縦読み（台帳の接続語で筋が通るか）。論点の回収（サマリの番号と最終ページの番号が対応するか）。証拠対応 |

## 3. スライド案（3 案）

1. `assets/components/` の断片から、設計図の型とレイアウト記述に合う型を選ぶ（下の一覧）。断片をコピーして、内容と数字を差し替え、`<名前>/slides/NN-A.html` に書く。
2. **3 案は、同じ型のまま配置・強調・密度を変える**（A: 標準／B: 強調や大きな数字を前に出す／C: 情報量を増やして密度を上げる）。基本として、**図と表を多用して説明する**。内容（文言と数字）は 3 案で同じ。
3. `python "<skill>/run.py" variants "<名前>"` → `<名前>/variants.html`。Playwright MCP の `browser_navigate` で `file:///C:/.../variants.html` を開き、「左の一覧から 1 枚ずつ見て、案を選び、直したい点はコメントに書いて、判断欄の右端の『回答をコピー』を押してください」と伝える。ページは、左に一覧（状態の点つき）、右に大きな 1 案と下に案のサムネ（押すと大きく見える）、コメント欄、前へ／次へ。見てほしい要素に付けた `data-note` は、枠と番号で重なる。ページの構成は、点検ページ（Artifact）と同じ。左に一覧（状態の点つき）、右に 1 枚ずつ縦に並べる（大きなスライド → 見どころ・前回のコメント・今回の直し → 判断欄）。スクロールして見る（1280×720〜1920×1080 で確認済み）。**`browser_resize` で窓の大きさを変えない**（窓とページの大きさがずれる）。3 択の下に「承認／要修正」のボタンがある（案を選んでいなければ、表示中の案が選ばれる。1 案だけのスライドはこのボタンだけで答える）。選んだラジオとボタンは、もう一度押すか「選択を外す」で外せる。「回答をコピー」は判断欄の最後の行（右端）にある（固定しない）。
4. 「回答をコピー」が押されるのを待つ（ユーザーに「完了」と入力させない）。押されると、回答はクリップボードに入り、同時に `window.__submitted` が立つ。`browser_evaluate` で次を実行し、送信されるか約 100 秒たつまでブロックして結果を返す。`submitted` が false なら同じ呼び出しを繰り返す（合計約 30 分、18 回まで）。ユーザーがターミナルに入力したときは待ちをやめて、その内容に従う。

   `() => new Promise(res => { const t0 = Date.now(); const id = setInterval(() => { if (window.__submitted || Date.now() - t0 > 100000) { clearInterval(id); res({ submitted: !!window.__submitted, md: window.__answersMd }); } }, 500); })`

5. `submitted` が true なら、`md` を `<名前>/answers-N.md` に書く（N は何回目か）。待ち受けずに、利用者がチャットに貼り付けた場合も、貼られた md を同じように書く。回答の形式は `## SNN` / `- 選択:` / `- 判定:`（承認・要修正。空でもよい。古い回答にはない）/ `- コメント:`。ボタンは「回答をコピー」の 1 つだけ（送信ボタンはない）。`finalize` は、判定が「要修正」のスライドも、コメントが残るスライドと同じく止める。
6. **コメントがあるスライドだけ**、選ばれた案を直して 1 案にし（`NN-A.html` を上書き、`NN-B/C` は削除）、`variants --round N+1` で再提示する（「採用／要修正」の選択になる）。ページには全スライドが出るが、**利用者には直したスライドだけ答えてもらう**（ほかは前回の選択のまま。未回答でよい）。別案の希望があるときだけ 3 案に戻す。コメントが未反映のうちは `finalize` が止まる。再提示のページは、前回のコメントを `answers-N.md` から自動で出す。**直した内容は `<名前>/round-(N+1)-notes.md` に「NN: 直した内容」の行で書く**と、同じスライドの「今回の直し」として並ぶ（書かなくてもよい）。
7. すべて決まったら、これまでの回答を**回の順に全部**渡す: `python "<skill>/run.py" finalize "<名前>" --answers "<名前>/answers-1.md" --answers "<名前>/answers-2.md"` → `final.html`（`build` が使う素のページ。変えない）と、確認用の `final-review.html`。後の回答が前の回答を上書きし、選択が空のスライドは前の回答を消さない。
8. `final-review.html` を `browser_navigate` で開き、「1 枚ずつ見て、『承認』か『要修正』を選び、『回答をコピー』を押してください」と伝える。待ち方と `md` の扱いは 4・5 と同じ（保存先は `<名前>/answers-final.md`）。『要修正』があれば、コメントに沿って `slides/` を直して `finalize` からやり直す。チャットで承認を受けた場合は、この手順は省いてよい。`finalize` を使わずにページだけ作り直すときは `review-final "<名前>" --answers …`（`finalize` と同じ引数）。

### 型の一覧（`assets/components/`）
各断片の先頭のコメント（用途・差し替える所）を読んでから使う。

本文の部品に共通の構成: 見出し（判断を言い切る 1 文）→ 図表タイトル（`data-role="lead"`。対象・期間・単位）→ 図表本体 → 注（`caption`。出典・前提・凡例）。箱・行・棒のすべてに定量（金額・件数・日数・%）を 1 つ以上書き、本文領域の下端（y 640）まで使う（空白帯を残さない）。**決定を求める型**（`decision`・`summary`・`side-by-side`・`options`・`risk`・`gantt`・表の `compare`・`rating`・`quote-compare`・`result`・`actions`・`raci`）は最下部に論点ボックス（パネル地の帯。「論点　〜の可否」1 行）を置く。**情報の型**（グラフ・`tree`・`layers`・`flow-h`・`cycle`・`pyramid`・`venn`・`before-after`・`before-after-h`・`cost`・`quote`・`effort`・`spec`・`issues`・`delta`・`matrix`・`timeline-h`・`timeline-v`・`cause`・`swimlane-h`・`swimlane-v`・`architecture`・`topology`・`org`・`roadmap`・`incident`）は帯を置かず、注の末尾を「→ 含意」の 1 文で締める。比較は型をそろえる: 工程の上下＝`before-after`、工程の左右＝`before-after-h`、体制・数量の左右＝`side-by-side`、案の評価＝`options`、工数＝`effort`（表）か `effort-bar`（横棒）、見積の前回比＝`quote-compare`（表）か `quote-bridge`（滝グラフ）、設備の増減＝`delta`（表）か `side-by-side`（左右）。

同じ内容に見せ方が 2 つある型は、対で持つ: 時系列は `timeline-h`（横。区間の長さで待ちを見せる）と `timeline-v`（縦。件数が多く文で読ませる）、業務フローは `swimlane-h`（横。レーン＝部門、工程 6 段まで）と `swimlane-v`（縦。工程 7 段以上）、構成図は `architecture`（上下の層）と `topology`（左右の系統）、Before/After は `before-after`（上下）と `before-after-h`（左右）。

配色の 3 役（面積の目安）: **ベース**＝白・パネル地（`--bg-soft`）・無彩色（文字・罫線・灰のグラフ）で面の約 70%。**メイン**＝基調色（`--accent`）とその階調（dark／soft／mid／light）で約 25%。濃い基調色は見出しの面・棒・縦線・小さな印に限り、大きな面（三角形・円・背景の帯）は淡い階調（`f-light`・`f-soft2`・半透明 20%）にする。**アクセント**＝強調色（`--emphasis`）で 5% 以下、**1 枚 1 点**（推す案・承認点・差の値）。

- レイアウト: `cover`（表紙）・`section`（章扉。題は章番号＋章の問い。下に「この章で判断すること」1 行と要点 3 つ）・`agenda`（目次。章ごとに結論 1 行とページ）・`summary`（数字サマリ。数字カード 4 枚（目標・差分・現状）＋根拠の表＋論点ボックス）・`decision`（クロージング決定。決定事項の表（サマリと同じ番号）・直近スケジュール・審議の基準の数字カード・論点ボックス）・`closing`（裏表紙。決定事項の再掲と承認後のアクション）・`incident`（障害概要。数字カード 4 枚（停止時間・影響範囲・損失・復旧手段）＋影響範囲の表（対象｜影響｜停止時間｜復旧時刻）＋現状の帯。論点ボックスは置かない）
- 図解: `flow-h`（手順。各段階に期間・成果物・承認点◆、下に全体期間の横棒）・`tree`（ロジックツリー。要因を寄与つきで分解し、末端の施策と評価列まで）・`pyramid`（階層。層に名前、右に権限と件数・金額・所要）・`cycle`（循環。各段階に指標・頻度・担当、中央に周期と KPI、右に 1 周目の実績）・`gantt`（フェーズガント。行見出しにフェーズ・内容・担当。完了＝塗り・計画＝枠線・現在線・判断点◆・論点ボックス）・`venn`（2 条件の重なりで候補を絞る。各領域に該当数と金額、右に抽出条件の表）・`before-after`（同位置の Before/After（上下）。工程が横に流れ、消える工程は同じ位置のまま破線）・`before-after-h`（同位置の Before/After（左右）。工程が縦に流れ、中央に差分列、下に LT の横棒。工程が 5〜6 段のときに使う）・`side-by-side`（左右比較。現行｜計画を体制・数量の同じ項目で行に並べ、右端に差分列）・`layers`（レイヤーマップ。層×系列の格子と、自社のリーチのブラケット）・`timeline-h`（時系列（横）。発生から復旧までの区間を、長さを時間に比例させた横棒で左から右へ。塗り＝作業・枠線＝待ち、上に区間名と所要・下に時刻、棒の下に節目（◆ 時刻　誰が何をしたか）、最下部に作業／待ちの内訳の帯）・`timeline-v`（時系列（縦）。左の縦線と点に沿って、時刻｜事象｜対応｜担当｜所要 を表で 8 行前後。点は発生・復旧＝塗り、待ち＝枠線。最大の遅れの行だけパネル地。件数が多く文で読ませるとき）・`cause`（原因の連鎖（横）。事象 → 直接原因 → 背景要因 → 根本原因 の 4 列を矢印でつなぎ、各箱に番号・名前・事実の数値。最下部に対策の行（枠線＝計画）と対策後の試算。要因を寄与で分解するときは `tree`、時間の連鎖で追うときはこちら）・`swimlane-h`（業務フロー（横）。レーン＝担当部門を帯で上から下へ、工程が左から右へ。工程の箱を担当レーンに置き矢印でつなぐ。判断は「◇ 〜判定」、採られない経路は破線、上に累計の経過時間、最下部に合計の帯。工程 6 段まで）・`swimlane-v`（業務フロー（縦）。列＝担当部門、工程が上から下へ 7〜8 段。左の軸に工程番号・時点と所要か成果物。枠線＝計画、関門の 1 工程だけ強調色。横に入らないときに使う）・`architecture`（システム構成図（上下の層）。層×役割の格子に箱を置き、現行＝パネル地・変更＝枠線・廃止＝破線・新設 1 箱＝強調色。層の間を矢印でつなぎ、通信の種別を添える）・`topology`（系統図（左右）。拠点とセンターを縦の集線で束ね、中央の回線で結ぶ。廃止＝破線に解約・新設＝基調色の実線、下に回線の本数の帯。層を上下で見せるときは `architecture`）・`org`（体制図。責任者（基調色の面）→ PM → チーム（パネル地）を直角の罫線で結ぶ。各箱に母体・人数・役割・専任／兼任、外部は破線の箱、専任の 1 チームだけ強調色の印。下に要員の合計の帯）・`roadmap`（更改ロードマップ。設備×年度のセルに増設＝塗り「＋n」・更改＝枠線「更 n」・撤去＝破線「▲n」を置き、切替の年度の列をパネル地で通し、右端に最終年度の台数）
- 表: `compare`（エグゼクティブサマリ。論点｜求める決定｜主要根拠｜詳細参照）・`rating`（論証テーブル。セルを「■ 事実 → ➢ 含意・打ち手」の 2 段で書き、論点ボックスを添える）・`options`（案の評価表。行＝評価軸と要件、列＝A/B/C 案。○△×と数値を併記し、推奨の列を強調）・`risk`（リスク｜影響（定量）｜対策｜残存｜オーナー）・`cost`（費用。費目×年度に 5 年計・構成比・累計）・`quote`（見積内容。項目×数量・単価・金額に小計・値引・消費税と見積合計の帯）・`quote-compare`（過去見積との比較。項目｜前回｜今回｜差額｜差の理由に合計行。差額の内訳を図で見せるなら `quote-bridge`）・`effort`（工数比較。工程×2 案の人日と差の表に、同じ行の比例棒と根拠。横棒グラフで比べるなら `effort-bar`）・`spec`（項目一覧。No｜項目｜観点・内容｜基準・要件値｜方法｜担当。検証項目・機能・要件に共用）・`result`（判定結果。総合判定の帯と、項目｜合格基準｜実測値｜判定（○△×）｜備考。項目の順は `spec` と同じ）・`issues`（課題・不具合一覧。No｜内容｜重要度｜対応｜期限｜担当｜状態。上に状態の集計カード、高で未完了の行を強調、期限超過の 1 セルだけ強調色）・`actions`（再発防止策。対策｜種別（■恒久／□暫定）｜内容｜期限｜担当｜状態。要の恒久策の行を強調、確定した期限の 1 セルだけ強調色）・`delta`（設備増減表。区分｜現状｜増｜減｜計画後｜差分に合計行、差分の合計だけ強調色。下に現状→計画後の横棒 2 本）・`matrix`（配置表。拠点種別×設備の台数。変わるセルだけパネル地に「現状→計画後」、最大の増設セルだけ強調色。右端と最下行に合計）・`raci`（役割分担表。工程×部門に ◎責任（1 工程 1 つ）・○実行・△支援。関門の工程の行をパネル地にし、その ◎ だけ強調色）。工程×時間の予定は `gantt`（図解）を使う
- グラフ: `bar`・`line`・`stacked`・`waterfall`（吹き出し版。グラフは全幅、図表タイトルと注つき。注目点は枠線の吹き出し 2 つまで。`axis` の max で吹き出しの余白を取る）と、所見が長文のときの `bar-note`・`line-note`・`stacked-note`・`waterfall-note`（グラフ×内訳表。左に見出し付きのグラフと吹き出し・注記、右にパネル地の内訳表（項目ごとの前提・数値・値に比例した棒。効く項目は基調色の縦線と濃い棒）と、合計を書く基調色の帯）。同じ構成の用途別の型として `effort-bar`（工数比較。左に現行と計画の合計の横棒、右に工程ごとの現行・計画・差と合計の帯。表だけなら `effort`）と `quote-bridge`（過去見積との比較。前回の合計 → 項目の増減 → 今回の合計の滝グラフ、右に項目ごとの理由・差額と合計の帯。表だけなら `quote-compare`）。円グラフ（`pie`）の型は置かない（`data-chart` の `pie` は使える。書き方は断片のコメントと下記）
- 内容に合う型がなければ、断片の部品（下記）で組む。新しい型を作ったら、`assets/components/` に足し、`check` で違反が 0 件になることを確かめる。

## 4. HTML の書き方

- 1 枚 = `<section class="slide" data-layout="…">`（1280×720px）。部品は `pp-text`・`pp-shape`・`pp-line`・`pp-image`・`pp-table`・`pp-chart` だけ。**これ以外のクラスの文字や図は PPTX に出ない**。
- 見てほしい要素（題・強調・差し替える所など、2〜4 点）には `data-note="題：結論の一文"` を付ける。レビューページが枠と番号で示す。同じ文を付けた要素は 1 つの見どころとして、枠でまとまる。PPTX には影響しない。型庫（`assets/components/`）の断片には付けてある。差し替えるときは、文が内容に合うかを見直す。
- 位置は `style="left;top;width;height"`（px）。文字には必ず幅を付ける。面と文字は兄弟要素にし、文字の中心を含む面が背景色になる。
- 文字: `data-role` = `title|lead|body|caption|display`。表紙・裏表紙の題と副題は `data-ph="title|subtitle"`（位置はテンプレート）。箇条書きは `<div class="pp-text"><ul><li>`。
- 色は `var(--accent)` などの変数だけ。基調色の文字は白地かつ 24px 以上のときだけ（薄い面の上の大きな数字は `num t-dark`）。**強調色（`f-emph`・`t-emph`）は 1 スライドに 1 点**（推奨・承認を求める対象）。
- 本文 14pt（約 19px）以上、注記 10pt（14px）以上。出典を書くときだけ、`data-role="caption" data-chrome` で本文領域の下端（`top:calc(var(--area-y) + var(--area-h))`。標準は y 640〜664）に置く。領域が標準より狭いテンプレートでは、出典が上がって本文と重なるので、`overlap` の指摘に従って本文の位置を直す。
- 視線誘導: 読む順は **Z の法則**（左上 → 右上 → 左下へ斜め → 右下）に従い、始点（題・結論）を左上、終点（承認を求める対象・結論）を右下まで届かせる。文の寄せ方は変えない（文は左寄せ。右寄せは数字の列だけ）。使える場面では次の 3 つも使う。**矢印効果**（矢印で読む順・因果を示す。循環は輪と矢印で回して見せ、直線の矢印だけにしない。矢印は矢じり付きで、手順・因果の図には必ず入れる）、**孤立効果**（目立たせたい 1 点だけ色・大きさを変える。強調色は 1 点）、**類同の法則**（同じ種類の要素は形・色・大きさをそろえ、違う種類は変える）。
- 画像はアイコン（`icons/<名前>-<accent|emphasis|white|gray>.svg`、`alt` 必須）と利用者の写真だけ。
- 重ねる図（ベン図など）は、重なる要素の両方に `data-overlap`。
- グラフ: `data-chart='{"type":"bar|barh|line|pie|stacked|stacked100|waterfall","categories":[…],"series":[{"name":"…","values":[…]}],"highlight":番号,"fmt":"#,##0","totals":[…],"axis":{"min":0,"max":600,"major":150}}'`。`axis`（任意）は値の軸の最小・最大・目盛の間隔を固定する。省くと自動。小グラフを並べるときは、全パネルに同じ `axis` を書く。ブラウザのプレビューは近似で、実際は PowerPoint のグラフになる。

### 描画の規準
- 配置の 4 原則: ①縦軸・横軸を決めてから置く（縦＝対象・分類・プレイヤー、横＝時間・工程・判断軸）。②同じ語を 1 枚に 2 度書かない。2 度出たら軸・見出しにくくり出す（軸ラベル・固有名・単位は数えない）。③1 つの図に 3 つ目の軸を持ち込まない。要るなら左右か上下に分ける。④数値の大小は、面積・長さ・太さに比例させる。
- 記号文法（全ページで同じ意味にする）: 実線（`pp-line`）＝実績・確定／破線（`dashed`。`pp-line`・`pp-shape` に付ける）＝予測・計画・消える要素／点線（`dotted`）＝補助輪郭。塗り＝実績・自社／枠線のみ（`f-outline`）＝計画・目標／濃色（`f-accent`・`f-dark`）＝主役、淡色＝文脈。比較では要素の位置を変えない。破線・点線は PPTX の線種になる。
- 階調: 基調色に白を 28・52・75% 混ぜた 3 段（`--accent-soft`＝`f-soft2`、`--accent-mid`＝`f-mid`、`--accent-light`＝`f-light`）。基調色を `#RRGGBB` で指定しても同じ式で作る。パネル地は `--bg-soft`（`f-soft`）、罫線は `--line`（`hr`）。
- グラフの作法: 軸は 0 始まり（％・指数は例外）。目盛は 3〜6。単位は図の左上に 1 回。全要素に実数ラベル（`data-chart` は自動で付く）。目盛線は出さない（自動で消える）。凡例を離れた場所に置かない（系列は 3 本まで。複数系列の凡例はグラフの直下に付く）。複数のグラフを並べるときは `axis` で軸をそろえる。実績と予測の境界は図中に示す。図表タイトル（`data-role="lead"`）は名詞句で、時点と単位を含める。1 枚に図を 2 つ以上置くときは、図ごとに図表タイトルを図の真上に置く。
- 表: 列幅は最長のセルで決め、語の途中で折り返さない。空のセルは空欄か「なし」（ダッシュで埋めない）。
- 本体は、本文領域の下端近くまで使い切る。無所属の空白帯を残さない。
- 禁止: 多色グラデ・3D・角丸の多用（`.r` は 2px）・全幅のカラーバー・署名・ダッシュ（—。題・本文・表・注記のどこにも使わない）。アイコンは使えるが、飾りにせず、ラベルを添える。

## 5. PPTX の出力

`python "<skill>/run.py" build "<名前>" [--footer "文言"]`。出力 JSON の `ok` が false なら、`violations` を読んで `slides/` の断片を直し、`finalize` からやり直す（内容は変えない。直すのは配置・サイズ・色）。直しが原稿の変更（文章を減らす、スライドを分ける）を伴うときは、案を示して利用者の承認を得る。

`ok` が true なら、`pngs`（確認用の画像。LibreOffice の描画）を開いて崩れを確認し、所見を伝える。PowerPoint で開いて最終確認することを勧める。成果物は `<名前>/<名前>.pptx`。

| rule | 直し方 |
|---|---|
| `overflow` | 文字の枠を広げるか、文章を減らす |
| `overlap` | 位置をずらす。意図的なら両方に `data-overlap` |
| `keepout` | テンプレートのヘッダー・フッターの領域（y 676 以降が標準）を避ける |
| `fontMin` | 本文 14pt（19px）・注記 10pt（14px）以上にする |
| `contrast` | 文字色か面の色を変える（基調色の文字は白地で 24px 以上） |
| `imageAlt`・`bodyImage` | `alt` を付ける／本文を画像にしない |
| `titleMissing` | `data-role="title"`（表紙・裏表紙は `data-ph="title"`）を付ける |
| `dash`（警告） | ダッシュ（—）を消し、接続語か読点で書き直す |
| `sameWord`（警告） | 同じ文言（6 字以上）を 1 枚に 2 度書かない。軸・見出しにくくり出すか、片方を消す |
| `orphanLine`（警告） | 最終行が 1〜2 字だけ。文字の枠の幅を変えるか、文を詰める |
| `emptyBand`（警告） | 本体が本文領域の下端より 120px 以上手前で終わっている。図や表を下へ広げるか、間隔を配り直す |

警告（`severity: warning`）は `ok` を false にしないが、5.1 で 0 件にする。`build` の前に見るときは `python "<skill>/run.py" check "<名前>/final.html"`。

### 5.1 工程5（計測で検証）
出す前（設計図と原稿の承認①の前と、PPTX を渡す前）に、次を自分で確認し、外れていれば直す。

- ヘッド: `lint-script` が空。加えて、完全文か・体言止めや数え上げがないか・実質数値は 2 つまでか・1 行（約 41 字）に入るか（入らなければ 2 行。それでも超えるなら設計図に戻る）。
- 数値: ヘッドの数字＝本体の数字（合計）。素材に無い数字は作らず、前提を明記した試算か「xx」で残す。
- 証拠: 設計図の証拠対応表のとおり、ヘッドの各節を本体の要素が証明している（文字の注記だけで支える節を残さない）。
- 論理: ヘッドを縦に読んで筋が通る。並列の要素は切り口 1 つ・粒度がそろう。論点の番号が、サマリの予告と最終ページの回収で対応する。
- 見た目: `build` の `violations` が、エラー・警告とも 0 件。線種と塗りの意味が全ページで同じ。確認用の画像に崩れがない。

手直しは 1 周。直せない項目は、利用者への報告に「未達」と明記する（理由も添える）。承認①の後で内容（文言・数字）を変える直しは、案を示して承認を得る。

## 6. 守ること

- 原稿の承認後は、承認なしで内容を変えない。
- 数字・固有名詞を作らない（素材に無い数字は、前提つきの試算か「xx」）。
- 仮想環境は、承認なしに作らない。既存の作業フォルダは、中身を見せて承認を得てから上書きする。
- エラーが出たら、原因と対処を示して止まる。推測で別の方法に切り替えない。
- スクリプトは Playwright MCP を使わない。MCP は、案の選択の受け取りと画面確認だけに使う。
